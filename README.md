# 🩺 About the Project

**MediFinder** is a Java web-based pharmacy locator and medicine-reminder platform designed to help users find nearby pharmacies, obtain directions when location access is limited, and manage personal medication routines through a unified digital system.

Instead of functioning only as a static pharmacy-listing page, MediFinder aims to connect:

**Users → Location / PIN Search → Nearby Pharmacy Discovery → Pharmacy Details → Directions & Location Fallback → Medicine Reminders → Dose Logs → Refill Alerts → Account Persistence & Administration**

The system is designed around the following primary users:

| User | Role |
|---|---|
| 👤 **User** | Searches nearby pharmacies, views address and contact details, uses location or PIN-based search, handles location permission and manual fallback, follows directions links, creates medicine reminders, records dose logs, and receives refill alerts. |
| 🛡️ **Administrator** | Manages users where supported, monitors system records, and accesses system-level information required for project governance. |

Additional role-specific responsibilities belonging to other assigned modules are maintained by the respective team members and recorded in the project SRS without being restated here as unimplemented features.

# 📄 Week 1 — Project Abstract

## MediFinder: Pharmacy Locator and Medicine Reminder Coordination System

**MediFinder: Pharmacy Locator and Medicine Reminder Coordination System** is a Java web-based platform designed to help users locate nearby pharmacies and manage personal medication routines through a unified digital system. Instead of functioning as a simple pharmacy-listing page, MediFinder connects **users, location-based pharmacy discovery, directions with location fallback, medicine reminders, dose logs, refill alerts and account-wise persistence** into a structured assistance workflow.

The platform is intended to allow a registered user to search for nearby pharmacies using location or PIN/address input, view pharmacy address and contact information, open directions links, and continue the flow even when browser location permission is denied through a manual location fallback. In parallel, the platform is intended to allow the same user to add medicine reminders, define schedules and repeat rules, record taken/missed/skipped doses, and receive refill-threshold alerts, with account-wise backend persistence.

The pharmacy-discovery lifecycle can progress through stages such as:

<p align="center">

`LOCATE` → `SEARCH` → `RESULTS` → `DETAILS` → `DIRECTIONS` / `NO RESULT` → `MANUAL FALLBACK`

</p>

The medicine-reminder lifecycle can progress through stages such as:

<p align="center">

`REMINDER CREATED` → `SCHEDULE ACTIVE` → `DOSE TAKEN / MISSED / SKIPPED` → `REFILL DUE` → `CLOSED / UPDATED`

</p>

## 📄 Software Requirements Specification

The complete Software Requirements Specification (SRS) contains the detailed system requirements, actors, functional modules, interfaces, constraints, security requirements and system workflow.

**📎 Complete SRS Document:** [SRS_DOCUMENT_LINK]

During Week 2, the team prepared the **Software Requirements Specification (SRS)** to formally define how MediFinder will operate and what the system must provide.

The SRS established the following core aspects of the system:

- **System actors:** User and Administrator, with clearly defined responsibilities, plus module-specific actions assigned to individual members.
- **Pharmacy discovery workflow:** User → Location / PIN Search → Nearby Pharmacy List / Map → Address & Contact → Directions or No-Result Handling → Manual Location Fallback.
- **Reminder workflow:** User → Add Reminder → Schedule / Repeat Rules → Dose Instructions → Taken / Missed / Skipped Log → Refill Threshold Alert → Account-wise Persistence.
- **Member 3 modules:** **M5 — Pharmacy Locator** and **M6 — Directions & Location Fallback**.
- **Member 4 modules:** **M7 — Medicine Reminders** and **M8 — Dose Logs & Refill Alerts**.
- **Remaining modules:** documented in the SRS as [Assigned modules] without unsupported implementation claims.
- **Technology foundation:** Java web project using JSP and Servlets, Tomcat as the application server, JDBC for database connectivity, [Database] for persistence, and HTML / CSS / JavaScript for page interaction, location permission handling and browser notifications.
- **Project boundaries:** MediFinder is planned as a responsive Java web platform. Native mobile applications, guaranteed push-notification delivery on all browsers, live courier tracking, online medicine payment checkout and clinical diagnosis remain outside the defined scope.

## 🔗 Entity Relationship Design

The ER design defines the relationships between the core system entities.

Key relationships include:

- A **User** can perform multiple pharmacy searches.
- A **Pharmacy** can appear in multiple search results.
- A search may end in a **directions link**, a **no-result state**, or a **manual location fallback**.
- A **User** can own multiple **medicine reminders**.
- A **Medicine Reminder** can have a schedule, repeat rule and multiple **dose logs**.
- A reminder can generate **refill alerts** based on a threshold.
- Notification preference is stored account-wise and remains subject to browser limitations.
